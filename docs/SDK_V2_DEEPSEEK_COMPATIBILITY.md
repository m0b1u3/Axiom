# DeepSeek 原生 V2 兼容与本地真实验收

2026-10-29，本地修复并完成真实请求验收。项目仍使用 Security SDK 0.5.0 / Codex 0.163.0，协议仍为 Responses，独立复核仍使用原生严格 Schema。本次未部署 VPS。

## 原因与真实对照

任务正文没有在父任务参数、SDK 保存或 Axiom 转发时被裁掉。父任务工具参数中的完整正文，与 SDK 子线程保存、SDK 发出的 HTTP 请求及 Axiom 转发后的任务正文一致；适配前后的完整 `agent_message` 对象规范化哈希也一致。

SDK 原生 V2 将任务作为 `agent_message` 发送，正文放在名为 `encrypted_content` 的块中。本次 DeepSeek 生成的派发参数实际是明文，但 DeepSeek Responses 接口忽略了这种内部消息类型。HTTP 200 只表示请求成功，未证明该输入项被模型消费。

随后绕过 SDK 和 Axiom，向同一接口发送四个固定严格 Schema 请求。任务、模型和 Schema 保持一致，每步只改变一个表示因素：

| 请求 | 相对上一项的改变 | 实际结果 | 输入 Token |
| --- | --- | --- | --- |
| A | 原始捕获的 `agent_message` | 未收到任务标识 | 138 |
| B | 只将任务块表示改为 `input_text` | 未收到任务标识 | 138 |
| C | 只补充 `role=user` | 未收到任务标识 | 138 |
| D | 只将 `type` 改为标准 `message` | 准确返回随机标识 | 200 |

四次均为 HTTP 200、Responses、`json_schema / strict=true`。前三次连输入 Token 都相同，最后仅改变消息类型便读到了任务。这将丢失边界定位到 DeepSeek 对该输入类型的解析，也确认 SDK 的内部消息格式需要第三方兼容处理，而非用户填错模型参数。

## 修复范围

- SDK 本体和 V2 工具保持原样。仅在 provider 为 `deepseek`、端点为 `https://api.deepseek.com`、运行环境为原生 V2 时，将该内部消息转换为标准用户消息。
- SDK 原有的发件人、收件人和消息类别文本、正文与内容顺序全部保留；不改工具参数、报告 Schema 或源码证据规则。
- 隐藏块必须逐字匹配此前已观察到的原生 V2 派发工具明文参数，或同次请求携带的派发历史。只保存明文哈希，不额外记录正文。不解密未知内容，无法证明来源、含未知内容类型或存在不可保留引用时明确拒绝发送。
- SDK 消息参数已经改变时不会猜测补回正文，也不会回退到 V1、Chat 或 JSON 模式。没有新增代理层重放，重试仍由 SDK 负责。
- 新 DeepSeek 任务默认使用官方 V2 包。旧 V1 结果、旧 Deep 续扫绑定及显式兼容连接配置继续保留，不将历史私有状态静默迁入 V2。其他连接的行为保持原规则。

脱敏机器记录见 [真实请求定位与修复验收](acceptance/deepseek-v2-message-fix-20261029.json)。此前的 [原生 V2 失败探针](acceptance/deepseek-native-v2-probe-20261029.json) 和 [V1 完整验收](acceptance/deepseek-runtime-isolation-20261029.json) 保留原事实，不回写为成功。请求原文、响应、账户和凭据不随源码交付。

### 根据实际失败定位的修复

- **Deep 工作进程凭据**：协调进程有 DeepSeek 凭据，SDK 派生 MCP 进程没有收到对应环境变量。现在通过 SDK 原生单次 MCP 配置补充所选环境变量的名称，不把密钥值写入配置，不修改插件文件。
- **续扫身份与清理**：原目录准备误用了新 attempt 的执行收据身份，提前失败还可能留下传输句柄。现在分别绑定原目录和新执行身份，失败路径也关闭传输；真实续扫仍为同一原生 Scan ID、父线程及检查点。
- **组件预算**：原来仍将 `maxCostUsd` 交给 SDK 内置价格表，因其不认识 `deepseek-flash` 而拒绝。现在每组件按平台冻结单价和自己的完整 Responses 用量控制额度，SDK 继续负责原生组件调度；SDK 金额不覆盖平台金额，缺用量继续阻止后续请求。
- **组件源码摘录**：完成前必须运行已有完整行校验，不能只依赖 SDK 草稿保存成功；同时修复辅助 CLI 经 `/var` 别名或符号链接入口运行时可能空执行的问题。调用端还必须收到有效校验结果，显式错误行号、缩进和半行摘录继续拒绝。
- **V2 消息抢占与用量**：真实流在子任务消息到达时被 Codex 原生抢占，尚未收到终态用量，触发预算保护。核对 [Codex 0.163.0 原始代码](https://github.com/openai/codex/blob/rust-v0.163.0/codex-rs/core/src/session/turn.rs#L2913) 后，仅有限预算组件执行启用原生 `defer_mailbox_preemption`，将消息留到下一个输入边界。本开关在该版本标为 under development，须随版本继续回归；没有吞掉缺失用量或改成 V1。
- **原生匹配 Schema**：DeepSeek 拒绝 Zod 生成的裸嵌套 `anyOf`。两个真实对照请求只改变 Schema 中 OR 的嵌套结合形式：原形 HTTP 400，等价展开后 HTTP 200；其余输入、模型及严格模式保持相同。适配只限当前 DeepSeek 官方端点和 V2，保留所有约束，涉及引用的 Schema 保持原样，SDK 仍按原始合同验证返回值。
- **验证临时链接归档**：任务 23 的审计和匹配均成功，但发布器正确拒绝 SDK 临时验证目录内的符号链接。现在只把 `artifacts/tmp` 中的链接本身移入私有 runtime，记录目标字符串哈希，绝不跟随目标；普通文件和 SDK 正式结果不改，其他位置的链接仍由原发布器拒绝。真实失败样本的副本经处理后，原生合同和发现内容保持一致；完整隔离发布测试通过。任务 26 未再次产生链接，不能将它表述为该分支的第二次真实触发。

任务 12、13、19、21、22 的部分结果，主动取消的任务 20，以及未能封存的任务 23 均保留原状态。任务 16 虽由应用显示 completed，独立校验发现证据结束行错误，因此明确不计为验收通过；没有改写旧结果，也没有从任务 23 未封存的 JSON 伪造提交。

## 2026-10-30 匹配用量与费用的隔离补齐

跨组件匹配现在单独归档 Responses 用量，并使用本次冻结单价生成平台估算。整次执行合并组件与匹配的独立回执，由服务端重新计算；旧 SDK 匹配费用标记、旧金额及旧归档保持原值。完整回执可估算，缺数据或失败时保留未知和已知下界，缺缓存写入仍为 null。单组件重试没有匹配请求且用量完整时，本轮估算可以已知，父计划仍可因其他未完成组件保持 partial；已知估算不能被人工核对覆盖。

该轮通过 348 项 Scanner、511 项合同、102 项 Web 单元测试，四个 API→Agent→Scanner 专项链路、历史读取与浏览器的完整/未知/部分费用、下载和执行身份检查通过。原本地 32 次执行、652 个归档及历史价格、费用未改变。全部模型边界由只允许环回请求的 Fixture 替代，真实模型请求为 0，未部署 VPS；此记录不构成新代码的真实模型验收，也不补算上述任务 26 的未知匹配费用。见 [隔离机器记录](acceptance/component-matching-usage-20261030.json) 和 [计价边界](MODEL_PRICING.md)。
